### IS-A Relationship (Inheritance)

An IS-A relationship represents inheritance in OOP. It means one class is a type of another class.

**Examples:**
- Dog IS-A Animal.
- Car IS-A Vehicle.
- Manager IS-A Employee.

**Why is it needed?**
1. Code Reusability – Reuse properties and methods of the parent class.
2. Extensibility – Add new child classes easily.
3. Polymorphism – Use a parent class reference to access different child-class objects.

**Example in C++:**
```cpp

class Animal {

public:

&#x20;   void eat() {}

};



class Dog : public Animal {

public:

&#x20;   void bark() {}

};

```

Here, Dog inherits from Animal and can access its eat() method.

**Remember:**
- IS-A = Inheritance
- HAS-A = Composition/Association

Use inheritance when a child class genuinely represents a type of its parent class.





### HAS-A Relationship (Composition / Aggregation)

A HAS-A relationship represents a relationship where one class contains or uses an object of another class.

**Examples:**
- Car HAS-A Engine.
- House HAS-A Room.
- Library HAS-A Book.
- Computer HAS-A Processor.

**Why is it needed?**
1. Code Reusability – Reuse functionality of other classes.
2. Modularity – Divide a complex system into smaller classes.
3. Flexibility – Change or replace components without changing the entire system.

**Example in C++:**
```cpp

class Engine {

public:

&#x20;   void start() {}

};



class Car {

private:

&#x20;   Engine engine;



public:

&#x20;   void startCar() {

&#x20;       engine.start();

&#x20;   }

};

```

Here, Car HAS-A Engine because the Car class contains an Engine object.

**Types of HAS-A Relationship:**
1. Composition – Strong ownership. The contained object is considered part of the owner.
2. Aggregation – Weak ownership. The contained object can exist independently.

**Remember:**
- IS-A = Inheritance
- HAS-A = Composition / Aggregation

KISS – Keep It Simple, Stupid
- Keep code simple and easy to understand.
- Avoid unnecessary complexity and overengineering.
- Makes code easier to debug and maintain.
- Example: Prefer a simple function over complicated nested conditions.

YAGNI – You Aren't Gonna Need It
- Don't implement features until they are actually required.
- Avoid building functionality based on assumptions about future needs.
- Saves development time and reduces unnecessary code.
- Example: Don't build video calling if the application doesn't need it.

DRY – Don't Repeat Yourself
- Avoid duplicating the same logic throughout the codebase.
- Extract common functionality into reusable functions, classes, or modules.
- Makes maintenance easier and reduces inconsistencies.
- Example: Create one reusable function instead of repeating the same calculation.

QUICK REVISION:
KISS  = Simplicity
YAGNI = Necessity
DRY   = Reusability


Design patterns are reusable, proven solutions to commonly occurring software design problems.

Instead of solving a common design problem from scratch every time, we follow an established approach that makes code more maintainable, reusable, and flexible.
